# DPR — Dethrottled Programmatic Resolve (1.8.2)

## Codex implementation brief

**Purpose:** A dependable, script-friendly interface for **evidence-oriented bulk acquisition**: submit URLs or queries, receive usable content *or an honest, traceable failure*, and resume interrupted work without starting over. Single-item resolve is the building block; durable batch processing is the headline capability.

- **Release boundaries:** 1.8.0 = DNB; 1.8.1 = stabilization; 1.8.2 = DPR. Inspect the actual repository and existing contracts first. Reuse search, fetch/render, extraction, quality, provenance, corpus and auth; don't create another browser stack or independent acquisition pipeline.
- **Hard prerequisite — cancellation:** Audit and fix any underlying cancellation/capacity-release holes **before** building bulk on top. Cancel, timeout, worker crash and restart must release leases/semaphores/browser resources; prove repeated cancellation under load cannot deadlock or permanently exhaust capacity. If this requires a 1.8.0/1.8.1 fix, surface it as a release blocker rather than hiding it inside DPR.
- **Two single-item primitives:** **Query → selected source** (one by default, optional top-N, explicit criteria and alternatives/ambiguity when warranted); **URL → usable normalized content** with bounded automatic HTTP/browser escalation. Optional search→select→fetch convenience operation if simple. Do **not** claim the objectively “best” source or synthesize an answer without a separately enabled capability.
- **Script-first contract:** Versioned, stable JSON; deterministic tie-breaking where feasible; canonical URL, content/Markdown, media type, timestamps, acquisition path, source/provenance and selection/quality signals. Explicit completeness/truncation, cache state, and missing-versus-empty fields. Machine-readable outcome/error codes, retryability and appropriate HTTP status/`Retry-After` behavior. A 200 response, bot challenge or blank Markdown is not proof of usable content.
- **Bulk as a first-class API:** Submit bounded batches of URLs and/or queries; return stable job/item IDs; poll progress; retrieve results/errors per item; cancel; resume after process/host restart; retry failed or expired items without redoing completed work. Support partial success, deduplication/idempotency keys and explicit at-least-once/duplicate-execution semantics—do not promise exactly-once processing.
- **Durability and truthful accounting:** Persist enough state to reconcile abandoned/in-flight items after crashes. Make queued/running/succeeded/partial/retryable-failed/permanent-failed/cancelled states unambiguous, with attempts, timestamps and failure-stage details. Preserve an acquisition trace (attempted method, status, rejection/recovery reason, relevant evidence) subject to privacy/retention policy. A failure record is a useful result, not something to conceal.
- **Bounded and fair:** Validate limits for batch size, bytes, timeouts, concurrency, queue depth, retries/backoff, retention, browser use and total work budget. Apply backpressure and scheduling fairness so a 50,000-item batch cannot starve ordinary API/MCP requests. Make expensive operations, LLM use and persistent corpus writes opt-in; no surprise side effects.
- **Cache and freshness:** Reuse existing cache where sound. Expose hit/miss/stale and source-observed timestamps; define refresh behavior and idempotent repeated submissions. Do not mistake cached content for newly verified live content.
- **Security stays intact:** Derive trusted caller/scope from authenticated gateway context, never user-supplied privileged headers. Enforce DNB's egress, DNS pinning, redirect/host policies, per-caller isolation, quotas and permissions for both single and bulk work; prevent one caller accessing another's jobs, results or retained evidence.
- **Test the ugly cases:** Deterministic fixtures for ambiguous search, redirects, JS escalation, challenge/blank pages, truncated content, stale cache and malformed inputs. Stress mixed-success batches, concurrent clients, duplicate jobs, retries, repeated cancellation, mid-item worker death, host restart, lost acknowledgements, capacity reclamation, progress correctness and bounded resource use. Verify stable JSON, provenance, no accidental corpus writes and existing API/MCP regressions.
- **Prove the product claim:** Measure sustained throughput, p50/p95 latency, CPU/RAM, queue fairness and recovery on realistic mixed batches versus the existing workflow; report actual successes, partials, failures and rework after restart. Do not claim audit-grade compliance, superior ranking or competitor uniqueness without evidence.
- **Ship for real scripts:** Minimal curl/Python examples for one URL, one query, batch submit→poll→collect, and crash/restart→resume/retry. Document practical limits, error taxonomy, retention, selection criteria and what “success” means. Keep arbitrary schema extraction and generated answers out of v1 unless already trivial.

**Implementation freedom:** Choose the simplest reliable endpoints, persistence and scheduling design after inspecting the codebase. No new service by default; don't turn DPR into a general-purpose workflow engine.

**Release gate:** A non-agent script can submit a substantial mixed-quality batch, survive cancellation and a genuine worker restart, resume without repeating completed results, recover capacity, obtain independently traceable per-item outcomes, and coexist with responsive interactive/agent traffic. If cancellation, identity or durability cannot be proven, do not ship bulk as production-ready.
